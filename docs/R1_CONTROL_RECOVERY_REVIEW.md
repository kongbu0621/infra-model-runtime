## 检查问题

取消、降低预算、撤销处理许可或读取许可，与已发放调用的结果结算先后发生时，提交故障能否造成费用丢失、控制失效、重复发放或回执身份改变？

新增[四项检查](../tests/test_r1_control_recovery.py)覆盖四类控制 × 两种先后顺序 × 两个被打断操作位置 × 四个提交窗口，共 **64 组**。每组使用独立的临时合成库，先登记两个请求并发放第一个，再执行控制与结果观察。顺序是受控串行交错，不冒充本轮新增的多进程竞争。

| 注入窗口 | 调用方分类 | 实际持久结果与接续 |
| --- | --- | --- |
| 提交前故障，回滚成功 | not_committed | 全表保持故障前；重开后原操作可执行 |
| 进入提交调用但 SQL COMMIT 未执行即故障 | unknown | 本例实际未提交，调用方不能据此假设所有 unknown 都未提交；重开后核对并接续原操作 |
| SQL COMMIT 已执行但确认丢失 | unknown | 全表已提交；重开后原操作返回原回执，不重复写入 |
| 已知提交成功后返回故障 | committed | 全表已提交；原回执重放及重复重放均不新增 |

每次核对 STORAGE_ERROR、提交分类、准确操作身份及全部表记录。故障前的同一快照另做正常执行对照，以核对原子性；这部分使用同一实现，不称为独立实现证明。再以手工规定的最终不变量核对：只发放一次、用量 4、预留 0、执行占用 0；应用投影一致，未发放请求无费用；撤权和取消仍限制当前采用，获准历史保留，撤销读取许可后当前及历史结果均拒绝。预算降至零后已结算事实保留，第二个请求不能发放；原已发放请求始终 ALREADY_ISSUED。读取与拒绝后的完整快照保持。

这验证了“业务是否可采用”与“事实是否必须结算”的职责分离，也验证 unknown 的两个实际持久分支。异常为测试注入；实际 SQL COMMIT 在对应分支执行，不等于设备断电或网络服务故障。
