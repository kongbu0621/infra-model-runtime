# R2 响应可用性与完整性分类复核

2026-11-26，GX10 / Linux aarch64 / Python 3.12.3 / 本地 ext4。确认并修复一处公开入口错误分类：请求尚未捕获响应时，`read_payload(..., "response")` 与 `copy_payload(..., "response", port)` 原来返回 `INTEGRITY_FAILURE`，把正常等待或 UNKNOWN 状态误报为存储损坏。

修复/测试/实际公共候选安装固定为 `9536de7d7b3078497f392c409ddc9735c37f89ef`，版本仍为 `0.1.0a1`；准确 wheel、反例和结果见[证据清单](evidence/2026-11-26-r2-payload-review/manifest.json)。相对前轮 `8e52deb`，运行代码只改 `model.py`，其余 11 个模块不变；不改变存储布局、预算或发送规则。

## 入口语义与原记录

| 情况 | 读取 / 导出响应的结果 |
| --- | --- |
| 请求存在，尚未捕获响应 | `UNAVAILABLE / not_applicable`，与结果尚不可用的语义一致；没有导出意图或端口读写 |
| 发放后中断，或捕获事务回滚，没有持久响应 | 同样 `UNAVAILABLE`；UNKNOWN、原回执、额度与执行占用保持 |
| 已有捕获元数据，但正文记录丢失或损坏 | 仍为 `INTEGRITY_FAILURE`；拒绝不修改原件，不把真实损坏降为等待 |
| 已保存合法的零字节捕获 | 返回精确 `b""`，可以按原内容身份导出；空字节不等于未捕获 |
| 应用历史读权拒绝 | 仍先返回 `DENIED`，不通过可用性分类绕过应用权限 |
| 请求不存在 | 仍为 `NOT_FOUND`，没有新增记录或端口 I/O |

修复先复用原事务审计与应用读权检查，再检查响应捕获事实；内部 `_payload` 的完整性要求不放宽。异常仍带原 `('payload', namespace, request_id, role)` 身份。正常未捕获时不得返回伪造空响应、创建副本、重新调用模型或释放预算。取消不删除已发生调用的历史事实，配置/批准变动也不改变原准确内容身份。

## 反例与验证

- 新增五个测试方法，在旧源码和原 `8e52deb` 实际安装分别检出 26 个错误分类子例。包含两种协议、登记/取消/发放后/远端返回后/捕获提交前状态，以及恢复读权后的读取与导出。
- 修复后同组通过，并验证三类载荷丢失仍拒绝、精确恢复合成原行后可接续，三种零字节捕获可读且副本只写一次，权限拒绝优先、未知请求仍准确分类。失败及重复接续前后比较完整持久记录和预算，禁止重发。
- 初次测试准备中，精确恢复记录会改变 SQLite 导出行序，测试误拒了两个合法恢复；已改为比较排序后的完整记录，原诊断日志保留。上述 26 只计修正判定后、实际错误分类的反例，不包含这两条测试误判。
