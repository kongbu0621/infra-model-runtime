# R3 同库接缝与强制内容确认候选

2026-11-27。`0.1.0a2` 新增 `CoordinatorHost` / `HostedModelRuntime`。这是可审阅的源码与 wheel 候选；原项目安装仍为 R2 `0.1.0a1`。R3 整体及已有业务迁移尚未验收。R1/R2 的创建、可选副本导出和数据库版本保持。

## 谁拥有什么

| 责任 | 本增量 |
| --- | --- |
| 数据库生命周期、目录访问权限、原对象绑定及应用锁 | `CoordinatorHost.guard(path)` 在 Runtime 每次短事务外取得应用原锁，返回检查函数；进入、提交前及退出核对。宿主必须保护协调库及其目录，不能将新建 R2 文件的权限假设套到已有协调库 |
| 调用登记、配置、许可、额度、响应捕获及结算 | Runtime 独占 `rt_*`，在宿主原数据库内运行；不向应用暴露连接或私有表 |
| 准入、业务依赖、当前结果资格 | `ApplicationPort` 经同一事务的有界 SQL 端口读取声明的应用表、更新 `app_*`；异常使双方本次修改一起回滚 |
| 输入、wire、原响应的确定身份及准确内容 | 绑定一个 `ContentPort`，事务外写入和读回；登记确认与发放/结算分别持久记录 |
| 旧引擎与旧状态接管 | 宿主拒绝未经迁移验证的状态；本接口不清账、不停止旧进程；已结束历史可经显式 [ClosedHistory](R3_CLOSED_HISTORY.md) 接续累计与容量，未决历史拒绝接管 |

宿主与内容端口是可信的本地适配器，不是恶意插件沙箱。宿主锁必须覆盖所有参与同一控制顺序的应用写入；ContentPort 不能嵌套持有该锁或协调库写事务。宿主清理失败保留原事务异常；提交后单独发生的宿主清理异常保留 `committed` 和原操作身份。

宿主进入或首次绑定检查失败也携带原操作身份：写入前为 `not_committed`，只读为 `not_applicable`。宿主进入/退出期间即使捕获了重入错误，本次操作仍拒绝；退出时已提交的事实不能改报为未提交。停止信号和已有主异常保持。

## 入口与持久绑定

```python
from infra_model_runtime import HostedModelRuntime

# host、content、application 由消费者提供，path 必须已经存在。
runtime = HostedModelRuntime.attach(
    path, configuration_bytes, application, host=host, content=content,
)
# 中断或重新启动后只打开原绑定，不再次 attach。
runtime = HostedModelRuntime(path, application, host=host, content=content)
```

`attach` 在一个事务中创建 Runtime 表、宿主绑定及应用扩展表；已经存在任何 `rt_*` 对象时拒绝。失败不删除原协调库。布局为 `r3.hosted-store.v1`，与 R2 布局互拒；其他模型入口继续沿用 R2 请求、回执、配置和协议版本。

`rt_host` 固定宿主身份、内容端口身份及只读表名单；对象重开及每次操作都核对，不能通过改配置换一个空库来消除原账。宿主名单至多 32 个表，不能包含 `rt_*`；可按需声明 `sqlite_master` 供应用检查自身旧表布局。只读名单不赋予写权限。

名单须为无重复的 tuple，元素为以 ASCII 字母或下划线开头、只含 ASCII 字母/数字/下划线且至多 64 字符的字符串。非法容器、元素、数量或重复项在进入宿主 guard 前返回 `INVALID_INPUT`；先核元素类型，再做哈希去重。

R3 SQL 端口每次语句至多 4096 行、32 MiB 字符串/二进制结果、64 个参数且每个参数至多 256 KiB，保留 SQL 长度和执行步数限制；仅额外允许 `length` / `typeof` 两个检查函数。R1/R2 仍使用原 256 行、32 KiB 返回值、16 KiB 参数边界。禁止事务控制、附加数据库、触发器路径、私有表访问、回调重入及离开回调后使用端口。

## 正常链及失败接续

1. `submit` 将冻结请求、业务记录与输入/wire 暂存同事务登记。
2. `run` 在事务外按原内容身份确认 input 和 wire；同一短事务核业务当前资格、配置与批准、占槽及额度，提交一次发送资格。
3. HTTP 在事务外执行一次。原响应先捕获到协调库，再按原身份保存到绑定内容端口并准确读回。
4. `recover` 只接续原捕获的内容确认与本地结算，不发送网络请求；应用结果关联和用量结算同事务提交。
5. `read_result` 在交付前重读三类确认内容，再核当前应用资格、配置/批准与隔离状态。历史读取仍受应用读权约束，但不把历史输出追认为当前可用。

内容端口**是交付必需的确认来源**。协调库仍保存暂存输入、wire、捕获响应及解析结果，供首次内容确认和本地恢复；本增量不是“SQLite 已无正文”的主存迁移。一旦某槽标记已确认，内容缺失或不符必须失败，禁止从暂存静默重建、降级交付或再发模型请求。未确认但写入已经成功时，沿原身份只读确认，不新建内容槽。

登记不等于发送，内容持久化不等于采用，`status` 可报告已捕获而尚未结算。响应确认失败时保留原预留；发送后没有捕获时保持 UNKNOWN 和原占槽。取消或撤权不会抹去已发放调用的消耗；内部原响应保存和结算不受业务读取撤权阻塞。结算成功后 `recover` 可能因返回状态时读权被撤而报 `DENIED`，不能据此误判结算回滚。

`content-confirm` 的提交状态只描述协调库确认事务。即使该事务为 `not_committed`，外部内容也可能已经保存；`unknown` 可能对应实际已提交或尚未提交，`committed` 也不表示后续结算已完成。接续应使用原调用和原内容身份检查实际状态，不能新建请求或重发模型。所列提交窗口与正常恢复见 [复核记录](PR7_REVIEW.md)。

候选内容 I/O 没有自动重试或远端硬超时保证，故障时由调用者用原身份接续。已确认内容在读回后被外部破坏属于后续存储故障，不能宣称跨组件全局原子性或永不丢失。

显式 `copy_payload` 属于用户读取，内容 I/O 前后都检查读权；内部原响应保存/结算继续使用独立的恢复语义。内容读取释放宿主锁后，在发起首次写入前重新检查槽是否已被其他句柄确认，避免按过时的未确认状态重建丢失内容。该检查不构成协调库与 ContentPort 的跨组件锁：检查之后已经开始的外部写入不能被后来的状态变更原子撤回，并发外部删除/恢复仍不在全局原子性保证内。

若最新标记已确认，必须只读复核该槽的实际 bytes：匹配则接续原调用，不额外写内容；确实缺失或不符才报完整性失败。“另一句柄完成确认”本身不是损坏，不能仅凭状态变化拒绝正常恢复。相关合法交错与损坏对照见 [PR #7 再复核](PR7_REVIEW.md)。

## 验收与未完成项

验证来源与准确构建见 [R3 验证记录](R3_HOSTED_VALIDATION.md)。覆盖同库登记/结算回滚、宿主清理、只读表隔离、内容失效/丢确认、取消、批准撤销及 UNKNOWN 重启。两个协议的实际回环 HTTP、准确材料/纠错和真实 Ledger 消费由独立应用 PR 留证。

已结束历史的隔离接续见 [ClosedHistory](R3_CLOSED_HISTORY.md)。未完成：未决业务状态接管、完整应用迁移，真实部署和旧进程切换，应用全部历史接口适配，多模型并发，远端恢复能力、网络文件系统、设备断电以及真实模型质量与效果。此候选不承诺这些项目通过。
