## 增量验证

| 轴 | 场景与检查 |
| --- | --- |
| 捕获、结算提交窗口 | 两协议 × 两事务 × 提交未执行/提交成功但确认丢失/提交后返回失败，共 12 组。逐项检查错误身份与提交状态、原响应是否持久化、槽位、wire 字节与预算；重开后恢复只结算一次，不再发送 |
| 凭据预检期间的控制 | 用第二个 Runtime handle 在预检处分别取消、撤销批准、改目标及降低额度，共 4 组。发放事务重新拒绝，零发送、零预算发放，原登记回执不变；这是受控时序注入，不是多进程压力测试 |
| 相同请求被另一调用者先完成 | 预检期间由另一 handle 完成原调用，返回后只恢复已捕获结果；总共一次发送，预算和原响应保持 |
| 用量与输出资格 | 两协议 × 正常/输出非法/身份缺失/用量矛盾/有效但超预留用量/截断捕获，共 12 组。分别核对终结、当前输出、已用、预留、槽位、最终用量和隔离；缺身份仍保留已知下界，截断不假装完整事实 |
| DNS 总时限 | 保留产品实际隔离启动参数，在子进程内受控阻塞 DNS。必须先写出已进入 DNS 的标记及实际模块来源，再核对时限、未知结果和子进程已回收；没有真实 DNS/模型请求 |
| DNS 判定反例 | 注入 DNS 前的导入失败，新的测试必须在“没有进入 DNS”断言处失败；独立检查故意失败的来源，不能将早退出当成超时验证成功 |

恢复/计量的 29 组是四个测试方法中的子例，不与套件方法数累加。DNS 正常检查为另一个方法；故意失败的判定反例单独留证，不算产品测试失败或额外通过数量。所有恢复分支还核对原请求重放与原内容，应用结算计数通过持久表独立检查。
