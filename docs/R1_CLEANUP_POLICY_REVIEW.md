## 问题与修复

| 问题 | 原行为 | 修复与核对 |
| --- | --- | --- |
| 游标与保护回调清理覆盖主错误 | fetch 的中断或业务拒绝会被 cursor.close、progress/authorizer 解除时的异常覆盖；第一个解除失败还会跳过第二个 | 逐次调用记录主异常，保留原中断对象和原业务错误；始终尝试两项解除。没有主错误时清理失败仍报错 |
| 捕获清理故障后继续提交 | guard 的 finally 异常未把端口置为失效；可信回调捕获后可能继续 SQL 或提交 | 任一清理故障使端口持续失效；即使被捕获，也拒绝后续 SQL 和回调出口提交 |
| 示例许可字段被当成布尔真值 | `allowed='disabled'`、`readable='denied'` 等非空字符串可能被视为允许；非法修订也可提交 | 独立示例校验单一规则行、正整数修订及严格 0/1 许可；提交前 audit 和读取入口共同拒绝非法元数据，报 INTEGRITY_FAILURE |

许可语义仍由消费者拥有，Runtime 不新增业务权限解释器。SQLite INTEGER affinity 已转换的合法整数按存储类型核对；不把任意非空字符串当布尔值。独立示例的规则是单一 `demo`，不宣称覆盖任意应用表或恶意同进程修改。

如果 authorizer 在真正解除前失败，原回滚可能被它拒绝。该路径保留原错误码并报告 `unknown`，不能把连接随后关闭后的实际回读结果倒写成当时已确认回滚。测试另外检查独立连接所见的原库，并沿原身份接续。真实中断依旧向上传播，不伪造提交回执。
