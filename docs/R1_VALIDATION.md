## 重点判定

| 覆盖 | 实际观察与范围 |
| --- | --- |
| 登记/配置 | 原回执重放、不同输入冲突、A→B→A 新修订、默认切换保留旧目标；旧绑定修订变化/停用阻止发放；请求许可/能力取交集 |
| 原子发放 | 两个实际独立 Python 进程竞争最后槽/额度，仅一个得到许可，另一方 BUSY；获胜调用终结后另一方仍受累计次数上限限制 |
| 取消/撤权 | 分别验证已确定的先后顺序，并各执行一对实际进程竞争；先控制阻止发放，后控制保留原发放/预留；迟到结果不恢复当前采用 |
| 结算 | UNKNOWN 重开仍占槽；终结但缺最终用量只释放本人槽；部分用量、迟到增量、重复/旧观察、超额隔离与其他未决预留分别保持 |
| 组合失败 | 登记/发放/结算/取消回调实际写应用表后抛错，整库逐表前后相同；原输入恢复后成功，双方记录共同提交 |
| 提交确定性 | 提交前故障回滚；实际 COMMIT 后模拟确认丢失返回 unknown，重开看到已发放但不能再取得令牌；已知提交后的返回故障保留 committed |
| 端口与关联 | 禁私有 SQL/事务控制/跨库/PRAGMA；吞异常仍回滚，过期句柄拒绝，read 不可写；双向关联缺失和缓存错误不初始化为空；独立无业务表消费者另按持久登记计数拒绝 Runtime 行缺失 |
| 有界与当前权 | 严格类型/版本/UTF-8、登记容量与控制容量、排队期限和发放时间回退、历史仍核当前读权；控制容量耗尽不妨碍已有调用的取消/观察 |
| 独立性 | 无应用私有 import；最小 standalone 消费不需任何 app 表，独立应用示例只通过公共端口操作自身记录 |

发放竞争、取消竞争、撤权竞争各一对真实进程；这不是长期压力、所有调度顺序、真实 SIGKILL 或断电矩阵。提交确认丢失是在真实 SQLite COMMIT 完成后注入 Python 异常，不能当作设备断电通过。结果和用量均为受控合成输入，不能证明提供方报告可信。

实现过程中区分了“部分用量已知”和“最终用量确认”，避免终结观察缺用量时错误清掉剩余预留；增加了双向 audit、回调吞异常拒绝及当前读取时间参数。上述均属于本次未部署原型的实现收敛，不是现用业务事故或已有版本缺陷声明。
