## 按操作区分后果

| 操作 | 实际后果与责任 | 故障时可继续什么 |
| --- | --- | --- |
| 读取本地持久状态/已有结果 | 不发起生成，仍受读权、完整性、存储可用性和读取容量约束 | 无需新增生成预算；原记录不可读时明确报错，不把读取失败解释为记录不存在 |
| 无工具文本生成 | 会消耗服务资源、预算并可能外发输入；“可重新生成”不等于只读、免费或内容相同 | 能恢复原捕获就先恢复；缺终结证据保留未知；新生成只能是独立获准调用，不是原请求的重放 |
| 生成工具提案或关键动作建议 | 生成与真正执行是不同操作 | 生成成功不授予执行权；应用核对准入、当前对象与已选监督 gate 后，经原控制 owner 发放动作 |
| 实际工具执行/外部写入 | 由应用或既有执行/控制组件负责，本组件首期不提供此能力 | 按对应 owner 的原身份、幂等及恢复合同处理；不能套用文本重新生成策略重做现实动作 |

## 分开判断未知、占用和可用性

| 已确认事实 | 执行资源 | 预算与结果 | 后续行为 |
| --- | --- | --- | --- |
| 原记录确认未发放 | 不占执行槽 | 原登记/控制容量保持 | 原调用在期限内重新核当前条件后完成首次发放；不是已发放请求重试 |
| 已发放、远端终结未知 | 原调用相关槽继续占用 | 未核清预留保持；诊断材料不当合格结果 | 仅按原身份有限核对；共享约束无余量时阻止新发放 |
| 终结已持久确认、用量未知 | 幂等释放本人执行槽 | 保留未结算预留；合格结果按原合同和当前许可读回 | 新调用仍要满足全部共享预算与资源限制 |
| 终结与用量已确认、业务拒绝结果 | 按事实释放/结算 | 拒绝采用不抹去真实成本 | 应用另行决定是否创建关联的新调用 |
| 协调存储故障或关键记录不可信 | 不能据内存或读取失败释放 | 写入结果不明保留未知 | 停止该协调域新发放，先恢复核对；不宣称所有读取/控制在物理故障下仍可用 |

UNKNOWN 不是一个覆盖所有事实的单值开关。远端终结、输出完整性、保存、用量、取消分别记录。HTTP 超时、客户端退出、租约到期、取消请求被接受或远端返回 NOT_FOUND，单独均不足以证明原生成未发生/已停止/不计费。

既有共享资源和全局预算规则继续适用：只有真正不受耗尽约束影响、且全部适用约束都有余量的调用才能继续。两个 profile 指向同一 GPU、服务或账户，不能借改名、改组、新数据库或换模型绕开占用。独立数据库不自动共享限额；本组件不能阻止绕过其协调范围的请求。

## 新调用与原调用的关系

重新生成的目标是取得一个新的候选结果，不是确认旧调用失败。具体恢复选择和字段须在实现合同中固定，至少满足以下条件：

1. 原调用仍能准确查询；新调用独立身份并关联原因、原调用及决策依据。相同请求 ID 的重放不产生第二次发送，也不因默认配置变化重新路由。
2. 应用策略明确允许这类再生成；新调用重新核当前输入/依赖、能力、数据处理许可、取消、期限及已选关口。不得把“结果可再生成”当作绕过审批或重新外发的理由。
3. 原累计消耗、未知预留和资源占用保留；新调用另行预留。相同资源组没有剩余槽时仍等待/拒绝，不能为了连续性释放旧槽。初期并发 1 的消费者在此条件下仍可能阻塞后续模型调用；消除该限制需要能力证据或经验证的资源方案。
4. 有可核验的远端状态/取消能力时，查询绑定原服务、账户批准、调用标识及有限控制额度；定义证据完整性、终结含义和可见性滞后。取消确认与停止/费用结清分别核对；能力缺失时明确保持未知。
5. 旧响应迟到仍归原调用，对其终结、用量和保存幂等对账，不覆盖新结果，不撤销取消，也不自动恢复业务采用。需要选用哪一版由应用按当前条件作决定。

### 同一再生成意图的累计限制与取消

独立调用 ID 不等于新的业务意图。应用启用同一任务的再生成策略前，须持久登记其稳定意图、有限累计预算、最大发放次数和整体截止，并将各次调用绑定到该意图。原实际消耗及未核清预留计入剩余额度；换模型、换调用 ID、重启或并发申请不能重置次数、预算或期限。具体字段和数值在实现合同中固定；没有可执行上限时不启用自动再生成。真正独立的新任务按自身授权登记，不能仅靠重命名把原任务的继续执行当作无关任务。

业务意图的当前取消、期限、采用资格和策略修订由应用拥有；Runtime 仍拥有每次调用及所有适用资源/预算池的事实。普通关联不自动继承取消，应用必须显式定义整项意图与单次调用的取消范围。通过[同库事务集成](ARCHITECTURE.md#同库事务集成)，在发放事务中同时复核当前业务准入、原子预占意图剩余额度/次数及 Runtime 资源；不能先在事务外检查再无条件发放。取消或到期在先则阻止该意图后续发放，发放在先保留在途事实；丢提交回执仍沿原身份核对。不得取消一次调用就误取消无关业务，也不得给已取消的意图新建调用以恢复采用资格。

额度或期限调整须由获准的显式策略修订留痕，保留原消费和未决义务；不能延长旧调用已绑定的截止或复活过期发放资格。已取消意图不能仅凭增加额度恢复。该规则与[监督/修订链的整体限制](OPTIONAL_SUPERVISION.md#成本信息与恢复边界)一致，但不要求普通恢复安装监督模块。

### 意图预占必须接续到结算

意图限额不能只有发放前的预占。各调用的发放、用量和未结预留仍以 Runtime 持久事实为依据，应用保存意图归属及策略；意图汇总是这些事实的派生检查，不另建可独立清零的费用权威。若实现采用缓存汇总，须绑定准确调用及已应用的结算修订，并在原观察/结算事务端口内与 Runtime 更新共同提交。缺记录、断档、汇总不一致或提交未知时先按原身份核对，不能把缺失汇总当作零占用继续发放。

| 变化 | 意图级额度和次数如何变化 | 必须避免的错误 |
| --- | --- | --- |
| 发放提交确认或提交回执丢失 | 确认提交时计入已发放次数；提交未知时保留本次预占及未知，先查原记录，不伪造已提交；重放不再计一次 | 不能因尚未观察到网络发送、超时、失败或取消退还发放次数；确认事务回滚才撤销本次未生效预占 |
| 终结确认但用量未知 | 仅按原合同释放执行槽，意图级未核清预留保持 | 执行槽释放不能当作预算已结清；次数也不恢复 |
| 确认用量或重复/迟到结算 | 按原调用已确认用量与尚未核清预留推导占用；新观察只应用相应变化，重复或乱序观察不回退已确认事实，原调用不会重复累计 | 不能一边保留已结清的完整预留一边再加实际用量，也不能漏记迟到的更高实际用量；超出意图限额仍如实记账并阻止该意图新发放 |
| 意图取消、到期、业务拒绝或 gate 未满足 | 真实终结和费用仍结算，采用资格继续按当前规则拒绝 | 业务不可采用不是账务端口故障，不能阻止终结/成本落账，也不能抹去真实消耗或自动恢复任务 |
| 意外端口失败或组合提交不明 | 沿同一捕获、调用和结算修订恢复；保留未确认义务 | 不容许一侧结算成功、另一侧按旧余额发放；不为修复账目重新生成 |

例如同一额度单位下，一次调用预留 10，终结与完整实际用量 6 均确认后，该调用应贡献“已用 6、未结预留 0”；重复相同观察不再增加 6，迟到更高用量 8 应更新为已用 8；再收到旧的用量 6 不能退回 6。其他未决调用的预留保持独立，不能被本次结算释放。这个例子说明核对规则，不代表数值配置、实现或服务用量已验收。实际超预留仍遵守原共享池与目标隔离规则，意图限额不取代 Runtime 全局限制。

本候选没有“人工点击清除 UNKNOWN”或按固定时长自动退款/释放的出口。若未来要承担重复费用风险、扩大并发或迁移资源范围，必须另行规定明确授权范围、数值上限、持久决策和守恒验证；不能用管理便利功能暗改当前合同。

## 对外状态与责任

状态接口应报告被哪项具体约束阻止、已确认的原事实和缺少的证据，区分“等待共享执行资源”“未结算预算不足”“未核准目标”“存储不可用”等原因。字段名和展示状态在公共合同实现时定义，错误信息不泄露凭据或无权读取的输入。

应用负责业务采用、改判、关键动作和界面；Runtime 负责调用事实、有限核对及准入资源。可选监督关闭时基础查询/恢复独立存在；已经选择的 gate 不因评审模型故障而跳过。评审调用也服从上述资源规则，不能在资源耗尽时无限新增模型来诊断模型。

## 实现位置与验收

R1 固定事实轴、端口和证据要求，R2 保留串行合同，R3 验证消费者的普通功能与原历史。分组并发沿 R4 单独验证，真实查询/终结能力按 R5 的目标及模式留证。早期可用的获准端点小实验可为 R1 提供输入，但不能替代 R5 安装和实际服务范围；没有能力证据时，不把“将来可查”写成恢复保证。
